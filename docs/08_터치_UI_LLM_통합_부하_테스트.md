# 터치 UI + Local LLM 통합 부하·사용성 시험 계획

## 0. 먼저 답: 터치 UI와 LLM을 같이 돌릴 수 있는가

현재 실측만 보면 **가능성이 높다.** Xavier NX 8GB에서 `Qwen2.5-1.5B-Instruct Q4_K_M`를 `llama.cpp` CUDA로 실행했을 때 다음 결과가 기록되어 있다.

| 항목 | 기존 실측 |
| --- | --- |
| 모델 파일 | 약 941MB |
| RAM | 약 4.3/6.8GB 사용 |
| 남은 RAM 단순 계산 | 약 2.5GB |
| 생성 속도 | 약 27 token/s |
| 프롬프트 처리 | 약 413 token/s |
| GPU | 약 99% |
| 입력전력 피크 | 약 14.2W |

HTML/CSS/JavaScript UI 자체는 무겁지 않다. 실제 추가 점유의 대부분은 Chromium, Ubuntu 데스크톱과 화면 합성기가 차지한다. 단일 kiosk 창만 실행한다면 1.5B Q4 LLM과 공존할 여지가 있지만, 다음 이유로 아직 확정 판정은 아니다.

- 모델 파일 941MB는 실행 중 전체 RAM 점유량과 같지 않다. KV cache, CUDA buffer, 서버와 Python 프로세스가 더해진다.
- `RAM 4.3/6.8GB` 측정 당시 화면·브라우저·실제 앱이 같은 조건으로 실행됐는지 기록이 부족하다.
- Chromium, STT, 카메라/비전을 동시에 상주시킬 경우 공유 메모리 여유가 빠르게 줄 수 있다.
- Linux의 단순 `used` 값에는 cache가 섞이므로 `MemAvailable`, SWAP 증가, OOM 여부를 함께 봐야 한다.

따라서 현재 결정은 다음과 같다.

> **기본 구성은 Qwen2.5 1.5B Q4_K_M + llama.cpp CUDA + Chromium 단일 kiosk 창으로 잡고, 화면을 켠 30분 통합 부하 시험을 통과하면 확정한다.**

LLM 때문에 UI를 먼저 축소하거나 0.5B 모델로 내리지 않는다. UI+LLM 통합 측정에서 실제 메모리 부족이 확인될 때 최적화 순서에 따라 줄인다.

## 1. 이번 시험에서 고정할 작품 조건

| 항목 | 기준 |
| --- | --- |
| 보드 | Jetson Xavier NX 8GB |
| OS | JetPack 5.1.x / Ubuntu 20.04 계열 |
| 화면 | 7인치, 1024×600, 실제 터치 입력 |
| LLM 기준선 | Qwen2.5-1.5B-Instruct Q4_K_M |
| 실행기 | llama.cpp CUDA 우선 |
| UI 실행 | Chromium 단일 kiosk 창 |
| 수납 구조 | 2×2, 총 4칸을 `A/B/C/D`로 고정 |
| 중심 목적 | 오지에서의 의료 도움, 물품 찾기, 구조 문자 보조 |
| 전원 | 최종 배터리 설계는 보류. 시험 중에는 안정적인 기존 어댑터 사용 |

2×2 칸 번호는 UI, LED, STM32, 재고 DB에서 아래처럼 같아야 한다.

```text
┌─────────┬─────────┐
│ A 좌측상 │ B 우측상 │
├─────────┼─────────┤
│ C 좌측하 │ D 우측하 │
└─────────┴─────────┘
```

`1층`, `2층`, `drawer-1` 같은 과거 식별자를 섞지 않는다. 실제 기구 배치가 뒤집히면 A~D 전체 계약을 한 번에 바꾸고, UI만 따로 바꾸지 않는다.

## 2. 오지 생존형 UI 권장 구성

### 2.1 홈 화면

첫 화면에는 설명이나 9개 시나리오를 한꺼번에 늘어놓지 않고 네 가지 큰 행동만 둔다.

```text
┌──────────────────────────────────────────────────────────┐
│ SafeAid   AI 로컬 ●   문자 신호 △   GPS ●   15:42       │
├───────────────────────────┬──────────────────────────────┤
│  1. 즉시 위험 도움        │  2. 부상·증상 도움            │
│  의식/호흡/대량출혈/CPR   │  말하기 또는 직접 선택        │
├───────────────────────────┼──────────────────────────────┤
│  3. 의료 물품 찾기        │  4. 구조 문자                 │
│  A~D 위치·LED 안내        │  위치/인원/상태 확인 후 전송  │
└───────────────────────────┴──────────────────────────────┘
```

상단 상태는 실제 값을 받은 항목만 표시한다.

- `AI 로컬`: LLM 서버가 실제 health check를 통과했을 때만 정상 표시
- `문자 신호`: 모뎀 등록 상태와 신호를 구분해 표시
- `GPS`: 위치 시각을 함께 표시해 오래된 위치인지 알 수 있게 함
- `배터리`: 전원 설계와 측정 회로가 정해지기 전에는 가짜 퍼센트를 표시하지 않음
- `DEMO`: 모의 데이터가 하나라도 포함되면 화면에 항상 보이게 표시

### 2.2 의료 도움 흐름

```text
[즉시 위험 확인]
  의식 없음 / 정상 호흡 아님 / 멈추지 않는 대량 출혈
       ├─ 하나라도 예 → 고정 위험 카드·CPR·구조 문자 바로가기
       └─ 모두 아니오/모름 → 증상 직접 선택 또는 음성 입력
                                  ↓
                           LLM은 scenario_id만 분류
                                  ↓
                    검수된 고정 카드 + A~D 물품 위치
```

- 생명위험 질문은 LLM보다 먼저 실행한다.
- 각 질문은 체크박스가 아니라 `예 / 아니오 / 잘 모르겠음` 세 상태로 받는다.
- 사용자가 말을 못 하거나 LLM이 실패해도 터치로 3회 이내에 카드에 도달해야 한다.
- LLM은 진단, 약 이름·용량, 처치 문장을 생성하지 않는다.

### 2.3 의료 물품 화면

- 화면에도 실제와 같은 2×2 A~D 지도를 보여준다.
- 검색 결과에 `A칸`, 물품명, 수량, 만료 여부, LED 색을 함께 표시한다.
- `칸 열기`를 누른 뒤에는 `여는 중 → 열림 확인 / 열리지 않음` 상태를 구분한다.
- 열림 센서나 STM32 ACK가 없으면 `열림`으로 표시하지 않고 `명령 전송됨`까지만 표시한다.
- 만료 또는 재고 없음 물품은 추천·자동 개방에서 제외한다.

### 2.4 구조 문자 화면

전화가 불가능하고 문자만 가능한 상황을 전제로 하되, **문자도 기지국 신호가 없으면 전송되지 않는다.** UI가 이 차이를 숨기면 안 된다.

권장 단계:

1. 수신처 선택: 사전 등록 보호자/구조 담당자/검증된 긴급 수신처
2. 위치: GPS 좌표, 위치 획득 시각, 수동 위치 설명
3. 인원: 총인원, 부상자 수, 이동 가능 여부
4. 상태: 고정된 부상 코드와 필요한 도움 선택
5. 미리보기와 사용자 확인
6. 모뎀으로 전송 후 실제 결과 표시

문자 상태는 아래 네 가지를 구분한다.

| 상태 | 화면 문구 |
| --- | --- |
| 모뎀/신호 없음 | `지금은 전송할 수 없습니다` |
| 로컬 대기열 저장 | `전송 대기 중 — 신호가 생기면 다시 시도` |
| 모뎀에 제출 | `전송 요청됨 — 수신 확인 전` |
| 모뎀 성공 응답 | `전송 완료` |

실제 전달 확인을 제공하지 않는 모뎀에서는 `상대가 확인함`이라고 표시하지 않는다. `119`라는 이름은 해당 문자 경로와 수신처를 실제로 검증한 뒤에만 쓴다. 그 전에는 `구조 문자` 또는 `의료 도움 요청 문자`가 정확하다.

고정 템플릿 예시:

```text
[SafeAid 구조 요청]
위치: {latitude}, {longitude} ({position_time} 기준)
인원: 총 {people_count}명 / 부상 {injured_count}명
상태: {injury_codes}
이동: {mobility}
요청: {request_code}
장치: {device_id}
```

LLM은 이 문장을 자유 생성하지 않는다. 사용자의 음성이나 짧은 설명에서 제한된 필드를 추출하고, 최종 문자는 코드가 고정 템플릿으로 조립한다.

## 3. LLM을 UI에 넣는 방식

하나의 거대한 프롬프트로 전체 앱을 라우팅하지 않는다. 사용자가 누른 화면이 이미 의도를 알려 주므로 화면별로 작은 계약을 쓴다.

### 의료 화면 계약

```json
{
  "scenario_id": "bleeding|cut|burn|foreign_object|splint|hypothermia|heat|co|bite|unknown"
}
```

### 구조 문자 화면 계약

```json
{
  "people_count": null,
  "injured_count": null,
  "injury_codes": [],
  "mobility": "possible|difficult|impossible|unknown",
  "request_code": "medical|evacuation|supplies|unknown"
}
```

규칙:

- 출력은 JSON Schema/grammar로 강제하고 추가 키를 허용하지 않는다.
- 사람 수와 부상자 수처럼 틀리면 위험한 값은 사용자가 미리보기에서 반드시 확인한다.
- GPS 좌표, 신호, 시각, 장치 ID는 LLM 입력에서 복사하지 않고 센서·시스템 값으로 넣는다.
- `unknown`을 정상 결과로 인정하고 직접 선택 화면을 보여준다.
- 모델의 `confidence` 문자열과 자유 형식 `risk_flags`를 안전 판단에 사용하지 않는다.

## 4. 시험 전에 해결할 현재 UI 조건

현재 `smartaid-kit`은 시각 확인용 정적 데모로는 쓸 수 있지만, 그대로는 UI에서 실제 LLM을 호출하는 기능 시험이 되지 않는다.

1. `static/app.js`의 `fetchJson()`이 항상 `localDemoFetch()`를 반환한다. `DEMO`와 `LIVE`를 명시적으로 분리하고, LIVE에서는 실제 `/api/*`를 호출해야 한다.
2. `static/index.html`은 `styles.css`, `app.js`를 루트 상대경로로 참조하지만 Python 서버는 `/static/`만 제공한다. 서버 실행 시 자산이 정상 로드되도록 경로를 통일해야 한다.
3. 현재 음성 입력은 브라우저 `SpeechRecognition`이다. 최종 오프라인 시험에서는 Jetson의 로컬 STT API로 교체해야 한다.
4. 현재 앱 백엔드는 Ollama 호출 계약만 갖고 있다. 실측 기준선인 `llama-server`와 연결하는 adapter를 추가하거나 OpenAI 호환 로컬 endpoint를 호출하도록 바꿔야 한다.

따라서 시험을 둘로 나눈다.

- **RAM 예비 시험:** 정적 UI + 별도 llama.cpp 추론. 코드 연동 전 바로 가능
- **기능 통합 시험:** LIVE UI → 로컬 API → llama.cpp → 고정 카드. 위 네 조건을 해결한 뒤 진행

## 5. 시험 환경과 기록 준비

최종 배터리는 아직 정하지 않으므로 이번 결과는 배터리 지속시간 판정에 쓰지 않는다. 안정적인 어댑터, 액티브 쿨링, 실제 외함 또는 외함과 비슷한 통풍 조건을 쓴다.

Jetson에서 결과 폴더를 만든다.

```bash
RUN=~/projects/aidkit/results/ui_llm_$(date +%Y%m%d_%H%M%S)
mkdir -p "$RUN"
echo "$RUN"
```

환경을 기록한다.

```bash
{
  date
  cat /etc/nv_tegra_release
  dpkg-query --show nvidia-jetpack
  /usr/local/cuda/bin/nvcc --version
  sudo nvpmodel -q
  free -h
  xrandr --current
} | tee "$RUN/environment.txt"
```

성능 모드는 번호를 추정하지 말고 보드에서 확인한 뒤 고정한다.

```bash
sudo nvpmodel -q --verbose
sudo jetson_clocks
```

모니터링 전용 터미널을 연다.

```bash
sudo tegrastats --interval 1000 | tee "$RUN/tegrastats.log"
```

각 단계의 시작과 끝에서 아래 스냅샷을 추가한다.

```bash
date
free -h
ps -eo pid,comm,rss,%mem,%cpu --sort=-rss | head -n 20
```

메모리 판단은 `RAM used` 하나가 아니라 다음을 함께 본다.

- `free -h`의 `available`
- `tegrastats`의 RAM/SWAP 변화
- Chromium, `llama-server`, Python 프로세스 RSS
- 커널 OOM kill 로그
- 30분 동안 조금씩 계속 증가하는 누수 여부

## 6. 1차: 화면을 띄운 상태에서 바로 다시 하는 LLM 시험

### 6.1 LLM 서버 실행

모델 경로는 실제 GGUF 위치로 바꾼다.

```bash
cd ~/projects/llama.cpp
./build/bin/llama-server \
  -m ~/models/gguf/qwen2.5-1.5b-instruct-q4_k_m.gguf \
  --host 127.0.0.1 \
  --port 8080 \
  -ngl 99 \
  -c 1024 \
  -b 128 \
  -ub 128 \
  --parallel 1 \
  --threads 4
```

초기 기준은 짧은 분류에 맞춘다.

- context: 1024
- parallel: 1
- temperature: 0
- 최대 출력: 16~32 token
- 모델은 한 번 로드한 뒤 상주시킴
- 구조화 출력 Schema 적용

### 6.2 UI 실행

RAM 예비 시험은 정적 UI를 띄워도 된다. 기능 통합 시험은 4절의 LIVE 연결을 먼저 고친다.

```bash
cd ~/projects/aidkit/smartaid-kit
python3 app.py
```

다른 터미널에서 실제 1024×600 화면에 kiosk 창 하나만 띄운다.

```bash
chromium-browser \
  --kiosk \
  --no-first-run \
  --disable-session-crashed-bubble \
  http://127.0.0.1:8765
```

DevTools, 다른 탭, 브라우저 확장, VS Code GUI는 Jetson에서 열지 않는다. SSH 터미널과 로그는 외부 PC에서 본다.

### 6.3 같은 입력으로 재측정

기존 Xavier 시험에 사용한 프롬프트와 문장을 그대로 먼저 실행해야 화면 OFF/ON 차이를 비교할 수 있다. 이후 새로운 hold-out 문장으로 정확도를 측정한다.

순서:

1. 화면 OFF 또는 Chromium 미실행 상태에서 웜 추론 10회
2. kiosk UI만 띄우고 2분 대기
3. 같은 웜 추론 10회
4. UI 버튼을 계속 전환하며 같은 추론 50회
5. 30분 동안 1분마다 분류와 화면 전환 반복
6. 마지막에 첫 10회와 마지막 10회의 지연·RAM 비교

각 요청마다 다음 CSV 열을 남긴다.

```text
timestamp,phase,input_id,expected,actual,schema_ok,latency_ms,ram_used_mb,ram_available_mb,swap_used_mb,gpu_temp_c,cpu_temp_c,gr3d_freq,ui_action
```

## 7. 자원 시험 단계

| 단계 | 실행 상태 | 목적 |
| --- | --- | --- |
| A | OS + 터치스크린만 | 데스크톱 기준선 |
| B | A + kiosk UI | UI 순증가량 측정 |
| C | OS + LLM server | 기존 LLM 기준 재현 |
| D | B + LLM server idle | UI+LLM 상시 대기 여유 확인 |
| E | D + 50회 분류 | 실제 추론 피크와 누수 확인 |
| F | E + 로컬 STT를 순차 실행 | 최종 핵심 경로 확인 |
| G | F + 선택적 사진 분석 | 메모리 통과 시에만 실시 |

한 단계가 통과하지 못하면 다음 모델까지 동시에 올리지 않는다. 특히 STT, LLM, 비전 추론을 같은 순간에 실행하지 않고 요청 흐름에 따라 순차 실행한다.

### 자원 통과 기준

- 30분 동안 OOM, 프로세스 강제 종료, 화면 멈춤, 재부팅이 0회
- UI+LLM 웜 상태에서 `MemAvailable`이 계속 **1.0GB 이상** 유지
- 시험 시작 대비 SWAP 증가가 **256MB 이하**이고 계속 증가하지 않음
- 처음 10회 대비 마지막 10회의 RAM 증가가 **200MB 이하**
- LLM 웜 p95 지연이 **2.0초 이하**
- 화면을 켰을 때 LLM p95 지연 증가가 LLM 단독 대비 **20% 이하**
- UI 탭 피드백 100ms 이내, 화면 전환 p95 300ms 이내
- 열 쓰로틀링이 없고, 지속 온도는 80°C 미만을 목표로 함

`MemAvailable 1GB`는 절대적인 NVIDIA 규격이 아니라 이 작품의 운영 여유 기준이다. 수치가 근소하게 통과해도 STT 단계에서 무너지면 최종 통과가 아니다.

## 8. UI + LLM 기능 시험 데이터

### 8.1 의료 분류

| 묶음 | 수량 | 내용 |

| 정상 표현 | 108 | 9개 scenario × 서로 다른 표현 12개 |

| 생명위험 | 24 | 의식·호흡·대량출혈, LLM 이전 고정 분기 확인 |

통과 기준:

- JSON Schema 준수 100%
- 생명위험 24/24가 LLM 없이 올바른 고정 흐름으로 이동
- 부정·무관 발화에서 임의 의료 카드 자동 시작 0회
- 9분류 macro-F1 0.90 이상, 각 class recall 0.80 이상
- 실패 시 `unknown → 직접 선택` 복구가 2초 안에 표시

### 8.2 구조 문자 필드 추출

최소 40개 문장을 만든다.

- 인원과 부상자 수가 모두 있는 문장 10개
- 이동 가능/불가능/모름 10개
- 상태가 모호하거나 정보가 빠진 문장 10개
- 숫자·부정 표현·STT 오류가 섞인 문장 10개

검증 항목:

- 사람 수와 부상자 수를 뒤바꾸지 않는가
- 모르는 값을 임의로 채우지 않고 `null`/`unknown`으로 두는가
- 고정 enum 밖 문장을 생성하지 않는가
- GPS, 시각, 신호 값을 LLM이 만들어 내지 않는가
- 미리보기 수정 후 고정 템플릿이 정확히 만들어지는가

필드 exact match 95% 이상을 목표로 하되, 숫자·이동 가능 여부는 UI에서 항상 재확인한다.

### 8.3 문자 통신 실패 시험

| 조건 | 기대 UI |
| --- | --- |
| 모뎀 분리 | 즉시 실패, 재연결/수동 대안 표시 |
| SIM 없음 | 전송 불가 사유 표시 |
| 신호 없음 | 로컬 대기열 저장 여부 선택 |
| 약한 신호 | timeout 후 재시도 횟수와 대기 상태 표시 |
| 모뎀 성공 응답 | 전송 완료 시각과 수신처 표시 |
| 재부팅 | 대기 중 메시지 유실 없이 복원 |

성공 응답을 받지 않았는데 `전송 완료`가 표시되는 사례는 0회여야 한다.

## 9. 터치 사용성 시험

실제 7인치 화면, 실제 외함 높이, 장갑 또는 젖은 손을 모사한 조건에서 한다. 개발 PC 브라우저만 보고 통과시키지 않는다.

대표 과업:

1. 의식이 없는 사람의 도움 카드까지 이동
2. 화상 증상을 말하거나 직접 선택해 카드 열기
3. 붕대 위치를 찾아 A~D 중 올바른 칸 확인
4. LLM을 일부러 실패시키고 직접 선택으로 복구
5. GPS 없는 상태에서 구조 문자 작성
6. 신호 없는 상태에서 문자를 대기열에 저장
7. 잘못 입력한 부상자 수 수정
8. 홈으로 돌아가 다른 기능 시작

최소 팀 외 사용자 5명, 가능하면 8명에게 실시한다.

기록:

- 과업 완료 여부와 걸린 시간
- 잘못 누른 횟수
- 뒤로 가기/홈 찾기 실패
- 의미를 오해한 버튼 문구
- 스크롤이 필요한데 발견하지 못한 경우
- LLM 대기 중 중복 탭
- 구조 문자 전송 상태 오해

UI 통과 기준:

- 핵심 과업 성공률 90% 이상
- 홈에서 의료 카드까지 터치 3회 이내
- 주요 터치 대상 최소 56×56px, 권장 64×64px 이상
- 작은 아이콘만으로 의미를 전달하지 않고 텍스트 병기
- 글러브 조건에서 오조작이 발생한 버튼은 간격·크기를 수정
- LLM이 300ms 이상 걸리면 즉시 진행 상태를 표시하고 중복 요청을 막음

## 10. 메모리가 부족할 때 최적화 순서

1. Jetson에서 DevTools, VS Code, 다른 Chromium 탭과 불필요한 서비스 종료
2. Chromium 단일 kiosk, 애니메이션·대형 이미지·실시간 그래프 축소
3. LLM context 1024, parallel 1, batch/ubatch 128, 출력 16~32 token 유지
4. STT와 비전은 요청 때만 실행하고 LLM과 동시 추론 금지
5. UI와 LLM 프로세스 누수 확인 후 재시작 정책 추가
6. 그래도 부족하면 Chromium 대신 native Qt/QML UI의 메모리 실측 비교
7. 마지막으로만 0.5B/0.6B 모델을 평가하고, 정확도 통과 시 교체

스왑을 늘려 통과시키지 않는다. SWAP이 계속 늘면 UI 반응과 SD 수명이 나빠지므로 메모리 구성 실패로 본다.
